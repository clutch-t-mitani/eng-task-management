# 実装上の注意点と検証手順

## 実装上の注意点

### 作業規約

DBカラムの追加・削除・型変更・制約変更は、既存 migration を編集せず、新しい migration ファイルを作成して履歴を残す。一度実行された migration はスキーマ変更の履歴として扱い、後から書き換えない。

グループをプロダクト非依存へ移行する際は、追加 migration で旧 `groups.product_id` を削除する。既存グループと `group_issues` を保持し、プロダクト単位だった `display_order` は全体順へ正規化する。

この migration のロールバックは、全グループの `product_id` を一意に推定できる場合だけ許可する。空グループまたは複数プロダクト混在グループが存在する場合、旧 `groups.product_id NOT NULL` を安全に復元できないため、スキーマ変更前に例外を投げて中止する。ロールバックを実行する場合はメンテナンス中に行い、事前に各グループが同一プロダクトのISSUEを1件以上持つ状態へ整理する。

Controller は HTTP 入出力の受け渡しに留め、業務ルール、複数モデル更新、並び替え検証、削除可否判定、レスポンス整形は Service / Form Request / Resource に分離する。ステータスID、GitHub状態、空フィルター値などのルール値はハードコーディングせず、PHP 側は Enum / Const、フロントエンド側は constants に集約する。

### D&D 並び替えの API 呼出しタイミング

グループ間D&Dは `vuedraggable` の `@end`、ISSUEのグループ間・グループ内・未グループD&Dは `@change` で API を呼ぶ。フィルター適用中は表示中グループ・ISSUEだけを現在の表示順枠内で並び替えて、非表示項目の相対位置を維持する。ドラッグ中はローカル状態へ即時反映し、API失敗時は `fetchTable()` を再実行してサーバー状態へ戻す。

### ソフトデリートされたユーザー・エンジニアの FK 保持

`users` / `engineers` テーブルの FK は `ON DELETE RESTRICT`（PHP レイヤーでソフトデリートするため物理削除されない）。`IssueResource` では `->withTrashed()` でリレーションを取得し、削除済みの場合は「削除済みユーザー」としてフォールバック表示する。

### 日付管理

日付4項目は `issue_schedules` で管理し、すべてディレクターが手動入力する。工数管理はv1では行わない。

### ENUM カラム

`issues.status_id` は TINYINT UNSIGNED で定義し、アプリケーションの backed enum で値の整合性を保証する。ステータスの追加・変更は enum と将来マイグレーションで対応（要件定義の「後から変更可能」に対応）。

### GitHub連携（Webhook自動反映 + 再同期）

- **Webhook署名検証**：`'sha256=' . hash_hmac('sha256', rawPayload, secret)` と `X-Hub-Signature-256` を `hash_equals()` で検証する。Secret未設定・署名ヘッダ欠落・署名不正は401で即終了し、DB更新しない
- **Webhookイベント**：対象は `issues` イベントの `opened` / `edited` / `reopened` / `closed`。`transferred` を含むそれ以外はv1では202で受け取り、`SyncLog.status='skipped'` として調査可能にする
- **Webhook入力検証**：署名検証後、`X-GitHub-Delivery`（必須・100文字以下）、`X-GitHub-Event`、JSON形式、対象actionのrepository/issue必須項目を検証する。不正な場合は422、正常な対象外イベントは202とする
- **Webhook応答時間**：GitHubへは受信開始から10秒以内に応答する。failed delivery再送時のDB行ロック待機は最大2秒、表示順ロック待機は最大5秒とし、取得できなければfailedログを確定して500を返し、GitHubの再送に委ねる。両ロックを同時に最大時間まで待たせない実装とし、最悪ケースを性能テストする
- **delivery再送**：`sync_logs.github_delivery_id` のUNIQUE制約でdeliveryごと1行にする。同一deliveryの `success` / `skipped` は処理済み200、`failed` は同じSyncLogを排他ロックし、ロック取得後にstatusを再取得・再判定する。行ロック待機は当該transactionに限り最大2秒とし、取得できなければIssueを更新せずfailedログを確定して500を返す。この行ロックはIssue反映とSyncLog確定を行う同一transactionのcommitまで保持する。待機中に先行処理が成功していれば再実行せず、なお `failed` の場合だけ `attempt_count` を加算して最新結果で更新する。同時競合のUNIQUE違反時は後続transactionをロールバックし、確定済みstatusが `success` / `skipped` なら200、`failed` なら500を返す
- **Webhook transaction境界**：Issue更新・成功SyncLog・リポジトリ最終反映状態は同一transactionで確定する。失敗時はそのtransactionをロールバック後、別transactionでfailed SyncLogを作成または更新する
- **Webhook結果理由**：`skipped` は `error_message` に安定した理由コード（`unsupported_event` / `unsupported_action` / `pull_request` / `repository_not_registered` / `issue_closed_not_imported`）を記録する。failed再試行が再度失敗した場合も、別transactionで `attempt_count` を必ず加算する
- **リポジトリ特定**：Webhook payload の `repository.owner.login` / `repository.name` を小文字化し、`is_active=true` の `product_repositories` と照合する。`(owner, repo)` はUNIQUEとし、未登録または無効化済みなら202でスキップし、Issueは作成しない
- **連携先変更**：取り込み済みIssueが存在するプロダクトでowner/repoを別リポジトリへ変更しない。解除は `is_active=false`、同一リポジトリへの再連携はtrueへ戻す
- **PATスコープ**：再同期用の `GITHUB_TOKEN` には Public リポジトリのみなら `public_repo`、Private リポジトリを含むなら `repo` スコープが必要。Fine-grained PAT の場合は対象リポジトリで「Issues: Read-only」権限を付与
- **PR除外**：GitHub Issues APIは Pull Request も含めて返す。`pull_request` キーの有無で判別してスキップする（タイトルの先頭文字や issue 番号レンジで判断しない）。WebhookではIssueを反映せずHTTP 202、`SyncLog.status='skipped'`, `skipped_count=1` とする
- **open/closedの取り込み境界**：未登録Issueは `open` の場合だけ新規作成し、`closed` はWebhook・初回取り込み・再同期のいずれでも作成せず `skipped_count` に計上する。登録済みIssueは `open` / `closed` を問わずGitHub由来項目を更新する。再同期APIはこの両方を満たすため `state=all` で取得する
- **Upsertの冪等性**：`(product_id, github_issue_number)` のUNIQUE制約を最終防衛線とし、Issue単位の短いtransaction内で既存確認・insert/updateを行う。存在しない行への `lockForUpdate()` のみに依存せず、一意制約競合時は既存行を再取得してGitHub由来項目だけ更新する
- **表示順採番**：新規Issueの `display_order=max+1` は全プロダクト共通の順序である。database cache lock `github-import:display-order`（TTL 30秒、最大5秒待機）を採番前に取得し、Issue transactionのcommitまで保持してWebhook同士またはWebhook/再同期の同時insertによる重複採番を防ぐ。ロックを取得できない場合はWebhookでは500 + failed SyncLog、再同期ではIssue単位失敗として `failed_count` を加算し、後続Issueの処理を続行する
- **ツール独自項目の保護**：Webhook/再同期ロジックは更新時に `director_id` / `engineer_id` / `status_id` / `is_managed` / `display_order` / `issue_schedules` の各日付を **絶対に触らない**。GitHub側のIssueクローズ → ツール側ステータス自動「完了」も行わない（`github_state` バッジで視認のみ）
- **件数と続行方針**：`updated_count` はGitHub由来値が同値でも既存Issueを正常に同期した件数、`failed_count` はIssue単位の保存失敗件数とする。Issue単位失敗後も後続を処理し、最初のエラーのみを秘密情報なしで記録する
- **partial / failed判定**：レート制限、401/404、5xx、タイムアウト、Issue単位失敗のいずれでも、中断または完了時に `created_count + updated_count >= 1` なら `partial`、0件なら `failed` とする。レート制限時は `X-RateLimit-Reset` を「次回同期可能: yyyy-mm-dd HH:MM」として記録する
- **PAT未設定**：`GITHUB_TOKEN` が空のまま再同期ボタンが押された場合は `SyncLog.status='failed'`, `error_message='GITHUB_TOKEN 未設定'` を記録し、HTTP 500 ではなく 200 + body の `status` で返す（UI側でトースト表示）
- **SyncLogライフサイクル**：手動再同期はロック取得後・GitHub API呼び出し前に `running` でログを作成し、終了時に最終statusと `finished_at` を確定する。異常終了で `running` が残る場合があるため、排他判定にはSyncLogではなくキャッシュロックを使う
- **タイムアウト/retry**：HTTPリクエストのタイムアウトは30秒。接続例外と一時的な500/502/503/504のみ200ms間隔で初回に加えて最大2回（合計最大3回）retryする。401/403/404/422/429、その他の4xx、不正JSONはretryしない。`403` / `429` で `X-RateLimit-Remaining: 0` または `Retry-After` があればレート制限、それ以外の403は権限不足として記録する
- **再同期の所要時間**：1回の再同期は同期的に実行する（v1ではキュー化しない）が、最大100ページ・APIリクエスト受信開始から120秒を上限とする。次ページ取得またはretry前に残り時間を確認し、上限到達時は `sync_limit_exceeded` とページ数・経過秒数を記録して、反映件数に応じてpartial/failedで確定する。Webサーバー・PHP・プロキシのリクエストタイムアウトは130秒以上に揃える。Issue件数や運用環境がこの上限に適さない場合のキュー化は将来対応
- **再同期の排他**：database cacheの原子的ロック `github-sync:product:{product_id}` をTTL 3600秒・非待機で取得し、実行中の要求は409とする。所有者が `finally` で解放し、強制終了時はTTL失効後に再実行できる。自動テストでは設定値を短縮する
- **最終反映状態**：`product_repositories.last_synced_at` / `last_sync_status` は成功またはpartial時のみ更新する。失敗時は直近の成功/一部成功値を保持し、失敗内容は `sync_logs` で確認する

## 検証手順

```bash
# 1. Docker 起動
./vendor/bin/sail up -d

# 2. DB 初期化
./vendor/bin/sail artisan migrate --seed

# 3. フロントエンド開発サーバー起動
npm run dev

# 4. ブラウザで確認
# http://localhost:5173
```

### 確認項目

**認証フロー**:
- シードのディレクターでログイン → `/table` にリダイレクト
- ページリロードで認証状態が維持される
- ログアウト → `/login` にリダイレクト

**管理表**:
- プロダクト・エンジニア・ステータスでフィルタリング
- グループはプロダクト非依存。プロダクトフィルター時は、該当ISSUEのあるグループのみ表示される
- グループ間 D&D → リロード後も並び順が保持される
- グループ内・未グループ D&D → リロード後も並び順が保持される。フィルター中は非表示ISSUEの相対位置が維持される
- ISSUEタイトルクリック → GitHub Issueを別タブで開く
- ISSUE一括移動・管理表除外 → 選択したISSUEだけが更新される
- ステータスのインライン変更
- 日付4項目を手動入力 → リロード後も保持される

**グループ非依存化 migration**:
- migration 適用 → 既存グループと `group_issues` が保持され、グループ表示順が全体順へ正規化される
- 全グループが同一プロダクトのISSUEを1件以上持つ状態でロールバック → `groups.product_id` が `NOT NULL` と外部キー付きで復元される
- 空グループまたは複数プロダクト混在グループがある状態でロールバック → 復元不能なグループIDを含む例外で中止し、`groups.product_id` は追加されず既存データも変更されない

**プロダクト管理**:
- プロダクトの一覧・追加・編集・削除・表示順変更ができる
- プロダクト一覧からリポジトリ連携設定画面へ遷移できる

**ダッシュボード**:
- 年月選択・前月/翌月操作で対象月を切り替えられる
- 集計カード帯に総ISSUE・完了・作業中・期日超過・完了率が表示される
- エンジニア別一覧テーブルに担当ISSUE数・ステータス別件数・期日超過数・対象ISSUE一覧が表示される

**GitHub自動反映**:
- プロダクト詳細でリポジトリ（owner/repo）を登録 → `GET /api/v1/products/{id}/repository` が登録値を返す
- インターネットから到達可能なWebhook URL `/api/v1/github/webhook`、Content type `application/json`、GitHub側と一致する `GITHUB_WEBHOOK_SECRET`、イベント `Issues` を設定
- GitHubでIssueを作成 → 本ツールの「未追加リスト」に自動で並び、`is_managed=0`・担当者NULL・ステータス「未着手」になっている
- アプリに未登録のclosed Issueに対するWebhookを受信 → HTTP 202 + `skipped` となり、Issueは作成されない
- GitHubでIssueタイトルを変更 → 本ツール側のタイトルが自動更新され、担当者・ステータス・日付は保持されている
- GitHub側でIssueをclose/reopen → `github_state` バッジが `closed` / `open` に変わるが、ツール側ステータスは変わらない
- Webhook署名が不正なリクエスト → HTTP 401、Issueは作成/更新されない
- Webhook Secret未設定 → HTTP 401、IssueとSyncLogは作成/更新されない
- `success` / `skipped` の同一 `X-GitHub-Delivery` を再送 → HTTP 200、IssueとSyncLogは重複更新されない
- Webhook処理を500で失敗させて同一deliveryを再送 → 同じSyncLog行で正常反映され、`attempt_count=2`、`error_message=NULL`になる
- `X-GitHub-Delivery` / `X-GitHub-Event` 欠落、delivery ID長さ超過、不正JSON → HTTP 422、IssueとSyncLogは作成/更新されない。ヘッダとJSONは正常だが対象Issueの必須payload不足 → HTTP 422、Issueは更新されずfailed SyncLogが記録される
- 同一 `X-GitHub-Delivery` を同時送信 → 確定済みstatusが `success` / `skipped` なら後続もHTTP 200、IssueとSyncLogは1回分だけ更新される
- failedの同一deliveryを同時再送 → 待機側はロック取得後にstatusを再判定し、先行側が成功済みならIssue更新と `attempt_count` 加算を重複実行しない
- failedの同一deliveryを再送し、再度500にする → 同じSyncLog行の `attempt_count=2` となり、最新エラーが保存される
- 対象外イベント・PR・未登録リポジトリ・未登録closed Issue → `skipped` と対応する理由コードが同期ログに保存される
- Webhookの最悪ケース（表示順ロック待機を含む） → 受信開始から10秒以内に応答する
- failed deliveryの行ロックを2秒以内に取得できない → Issueは更新されずHTTP 500、failedログが確定し、後続の再送で再試行できる
- `transferred` を受信 → HTTP 202 + `skipped`、Issueの所属プロダクトは変更されない
- リポジトリにPRが含まれる場合、PRは取り込まれず `skipped_count` に計上される
- 「未追加リスト」で「管理表に追加」を押す → 当該行が管理表に移動し、未追加リストから消える

**GitHub再同期**:
- 初回取り込み前にGitHub側へopen Issueとclosed Issueを用意 → 「GitHubから再同期」ボタン押下でopen Issueだけが未追加リストに作成され、未登録closed Issueは作成されず `skipped_count` に計上される
- 初回取り込み後にGitHub側で新しいopen Issueを作成し、取り込み済みIssueをclose → 再同期で新しいopen Issueが作成され、既存Issueの `github_state` はclosedへ更新される。過去からclosedの未登録Issueは引き続き作成されない
- 取り込み済みclosed Issueをreopen → 再同期で同じIssueの `github_state` がopenへ戻り、重複作成されない
- 既存の取り込み済みIssueの担当者・ステータス・日付を編集 → GitHub側でタイトル変更 → 再同期。タイトルだけ更新され、それ以外は保持されている
- `.env` に不正なPATを設定して再同期 → トースト赤色 + `sync_logs` の `status='failed'`、`error_message` に401内容
- 同一プロダクトで再同期を二重実行 → 後続要求はHTTP 409、先行処理は継続する
- 再同期開始直後 → `status=running`, `finished_at=NULL` のログが存在し、正常終了後は同じ行が最終statusと終了日時へ更新される
- 排他ロック保持中に例外 → `finally` で解放される。強制終了を模した場合も短縮TTL失効後は再実行できる
- 1件も反映する前にレート制限/5xx/timeout → `failed`、1件以上反映後に同じエラー → `partial`
- 1件のIssue保存のみ失敗 → `failed_count=1`、後続Issueは処理され、成功件数が1件以上なら `partial`
- 接続例外/500/502/503/504 → 初回+最大2回（合計最大3回）retry、401/403/404/422/429・その他4xx・不正JSON → retryせず終了。`Retry-After` 付き403/429はレート制限、通常の403は権限不足として記録される
- 100ページまたは受信開始から120秒に到達 → 次ページ/retryを開始せず中断し、`sync_limit_exceeded` とページ数・経過秒数が記録され、反映済み1件以上ならpartial、0件ならfailedになる
- 取り込み済みIssueがある状態で別owner/repoへ変更 → HTTP 422、既存設定とIssueは変化しない
- リポジトリ連携を無効化 → 再同期ボタンが無効になり、再同期APIの直接呼び出しはHTTP 422を返す
- 成功後に再同期を失敗させる → `last_synced_at` / `last_sync_status` は直近の成功値を保持し、失敗は `sync_logs` に追加される
- 同期ログ一覧 → `trigger` / `github_delivery_id` / `attempt_count` を含み、`started_at DESC, id DESC`。`limit=1` / `100` は成功し、0 / 101 / 非整数は422
- スモークテスト完了後、検証用IssueとGitHub側のWebhook設定を削除する
